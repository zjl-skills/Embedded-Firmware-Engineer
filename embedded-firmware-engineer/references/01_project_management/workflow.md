# 工程接手与追溯

## 选择任务规模

| 任务 | 首先确认 | 需要保留的输出 |
| --- | --- | --- |
| 全新开发、整机集成 | 目标板、接口、资源和验收条件 | 基线、需求、模块契约、验证计划 |
| 增加功能、修改优化、重构解耦 | 现有入口、行为、受影响依赖及回归基线 | 增量设计、接口影响、验证差异 |
| MCU 移植、裸机升级为 RTOS、RTOS 重构 | 原平台行为、目标平台能力、时间与资源预算 | 差异表、分阶段切换方案、跨平台回归 |
| MCU 外设、外部器件或原理图驱动开发 | 料号、封装、网表、时钟及器件时序 | 可核对配置和驱动契约、异常测试 |
| Bug、审查、性能调优 | 复现方法、版本和观测证据 | 根因或审查发现、前后对比、回归结果 |
| 工具链和工程维护 | 实际目标、当前构建入口及已知可用版本 | 构建命令、产物、依赖与差异 |

沿仓库已有结构工作。已有项目优先读 `PROJECT_CONTEXT.md`、`PROJECT_BASELINE.md`、变更记录及受影响模块交接，检查分支、当前提交、未提交变更和构建入口。有效信息可以直接引用，局部任务只补需要的证据。未初始化的大型工作可选择 `.embedded/` 或现有管理目录。

## 建立或更新基线

1. 分类任务和工作模式，盘点目录、工具链、已有架构、目标 MCU 和 RTOS。区分配置线索与可运行的实际目标。
2. 读取工程资料、登记来源和范围，对冲突进行分级，批准关键硬件和需求基线。记录 Git 提交、板版次、封装、芯片修订、SDK/RTOS/编译器版本、启动与链接配置、构建命令、约束及可重复验证入口。
3. 按验收条件拆需求、设计模块、公共接口及异常路径。明确模块依赖、共享资源、并行边界、所有者和优先级。有依赖的模块在接口确定后进入实现。
4. 复用实际构建和测试入口，按模块验证、集成、系统验收逐层记录。设计或资料变更同步引用、验证计划和相关人员，再更新基线与变更记录。

## 需求追溯

为每项独立可验收行为分配稳定 ID。链路为需求 → 设计 → 模块 → 接口 → 代码 → 测试 → 验收。来源包含 Document ID 和位置，验收条件包含输入、预期、容差及环境。测试状态和验收证据分开记录；共享代码或测试可以被多项需求引用。

| 状态 | 推进依据 |
| --- | --- |
| Proposed / Confirmed | 已提出 / 来源、职责和验收条件已确认 |
| Designed / Implemented | 已关联批准的设计及接口 / 实现及代码位置已记录 |
| Verified / Accepted | 每条实现链有已通过的验证用例和证据 / 另外有批准的验收记录 |
| Deferred / Rejected | 有决策、原因及必要的恢复条件 |

生成追溯矩阵，检查无实现的需求、无验证的实现，以及已纳管代码和测试的悬空项。独立审查代码清单覆盖率和实际调用，落实项目确认的排除范围。参见 [命令与数据契约](../00_core/automation.md) 和 [质量验证](../07_quality_assurance/verification.md)。
