# 质量验证

选择覆盖本次改动风险的验证层，复用工程已有入口。记录命令、配置、版本、测试环境、证据引用和退出结果。

| 验证层 | 可声称的结果 |
| --- | --- |
| 编译、链接 | 各文件通过编译、目标完成链接，各自以日志和产物佐证。保留 warning、map 和资源变化。 |
| 静态与架构检查 | 指定分析器、规则、范围和未解析项。人工审查接口、边界、竞态、依赖和错误路径。 |
| 单元、集成、回归 | 独立模块行为、真实或明确替身下的接口协作、既有行为约束。记录场景、实际值和预期。 |
| 系统和硬件 | 在目标板或明确仿真环境执行的系统行为，给出板号、版本和测试条件。 |
| 验收 | 对照已确认需求的每条验收条件、环境和签收记录。 |

覆盖参数、边界、负载和失败路径，包括超时、空/满队列、最坏时序、资源耗尽、错误恢复、重复起停和长时间运行。测量 RAM/Flash、栈、CPU/功耗、实时响应时标明硬件和工具条件，并与基线及预算比较。

审查记录明确文件和行、严重度、影响、复现或触发条件和验证办法。集成对照公共接口、依赖和资源冲突，运行目标消费者的测试。`Verified` 需要已通过且有证据的用例，`Accepted` 同时需要明确的验收记录。真实硬件或专用工具缺失时记录范围和待验证项，继续执行可用的宿主和静态检查。

## 可核验的执行记录

`record_test_evidence.py` 运行明确授权的 argv，按要求记录 Test ID、Requirement ID、工具链版本、命令、环境、UTC 开始/结束时间、实际退出码和输出、预期行为、状态与日志 SHA-256。用 `--input` 绑定测试源及关键输入，执行前后比较散列。分类使用 `Host Unit Test`、`Host Integration Test`、`Target Build Test`、`Hardware Test` 或 `System Acceptance Test`。类别和目标细节按实际环境填写，通过宿主命令得到的结果只证明宿主范围。

结构化策略重算日志和输入散列，从日志核对命令、环境、退出码和实际输出，检查 Test/Requirement 归属。需求的 `verification_kinds` 可列出所需验证层。`Accepted` 额外需要批准者、时间、独立授权记录的散列及与当前所有关联证据匹配的清单。工具检查完整性与关联，批准者身份、命令是否覆盖验收条件及实板真实性由工程评审核验。[字段与旧证据迁移](../00_core/automation.md)
