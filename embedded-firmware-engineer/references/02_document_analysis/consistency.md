# 资料治理与一致性

## 登记与权威性

`DOCUMENT_REGISTRY.md` 记录采用的数据入口及项目约定。使用工具时以 `documents.json` 为每份资料的登记来源，分配稳定 Document ID。记录名称、相对于项目的路径、资料类型、声明版本、磁盘更新时间、散列、范围、权威角色、模块、需求、关联资料、状态和最近核对时间。外部受控资料可登记经授权的本地副本，并注明来源；用项目原有资料库时保存引用和可复现的版本标识。

状态含 `Valid`、`Pending Confirmation`、`Conflict`、`Outdated`、`Superseded`、`Archived`。新发现资料待确认。改动时间用于定位文件，权威性按实际适用范围与批准记录确定。将参数、协议、需求等事实维护在一个批准的位置，其他引用带 Document ID/版本/定位。

## 一致性检查

从资料中抽取可复查的原始定义，放入 `facts.json` 或项目等价表。显式归一化板版次、范围、器件变体、单位、编码和时序方向。分类检查 MCU、引脚、电源/电气、协议、需求、时序、架构、版本及硬件能力与软件需求。`validate_project.py` 对同 `category + key + scope` 下的活动资料明示值给出冲突候选和证据，适用范围待确认的定义单独提示。工程解释包括范围重叠、数值窗口、兼容性、依赖和容差，按相关资料审查。

1. 在 `ISSUES.md` 记录 `ISS-...`、严重度、板和软件范围、原始定义及文档定位、相互差异、风险、受影响任务、建议和可继续事项。工具的 `CF-...` 可用作跨报告关联。
2. P0 涉及硬件正确性、核心需求、安全或关键架构。冻结相关工作链路，提供候选决策并等待必要批准。P1 涉及模块设计或功能，优先协调，继续独立部分。P2 记录假设、依据及处理结果后推进。
3. 在 `DECISIONS.md` 记录批准者、备选、选择、理由、适用范围、技术影响及证据。按决策更新权威来源的状态、事实和依赖引用。保留旧版本的出处与继任关系。

## 文件变更到技术影响

1. 用 `check_document_changes.py` 对比已记录 SHA-256 和可识别的版本标记。相同哈希的时间戳变化属于元数据变化。有两份可读快照时核对文本差异，其他文件需要原生比较或批准的可解析导出。
2. 复核具体技术变化和范围。使用报告列出的关联文档、需求、设计、接口、代码和测试候选，沿实际依赖继续检查受影响项。给出临时影响等级、有依据的最终等级和需要重测的边界。
3. 填写 [资料变更影响报告](../../templates/reports/DOCUMENT_IMPACT.md)，记录用户决定、批准后的同步和仍待降级的假设。记录原始版本、新版本、校验值和变更编号。
4. 经批准后按哈希推进登记基线，同步权威资料和受影响记录，再执行结构化一致性、追溯、构建和必要回归。保持文档与代码引用同一次决策，独立拒绝或延迟的项保留审查记录。
